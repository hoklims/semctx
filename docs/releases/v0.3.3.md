# v0.3.3: a change-impact report that decides no proof

Semctx 0.3.3 adds `semctx impact diff`, which emits `ChangeImpact` v1: what a change can affect,
through which link, with what confidence, and where the modeled reach stops. It changes no index
format, verification-state format, MCP tool or existing JSON contract.

## Install or upgrade

Semctx 0.3.3 requires Bun >=1.4.0. Pin the release when reproducibility matters:

```bash
bunx semctx@0.3.3 install
```

Plugin installation does not reload an active agent session. Open a new Codex task, or run
`/reload-plugins` in Claude Code and restart if reload fails.

## What changed

`verify diff` answers two questions in one report: what a change can affect, and whether it is
acceptable. Its `verdict` mixes impact, proof sufficiency and index admissibility, so a proof
planner that wants only the first answer could not get it without inheriting the second. A small
replay change in a consumer repository was requalified far beyond its real reach because nothing in
the machine output said where the reach stopped, or why (ADR 0030).

`semctx impact diff` produces a separate, versioned report (`kind: "change_impact"`,
`schemaVersion: 1`) for the working tree, the staged diff or a range:

```sh
semctx impact diff [--base <ref> [--head <ref>] | --staged] [--surfaces <map.json>] \
  [--format text|json] [--output <path>]
```

- **Tiers are kinds of links, not scores.** `directlyAffected` and `transitivelyAffected` rest on
  behavioural links the graph resolves (calls, same-file references, test imports by name);
  `possiblyAffected` rests on a structural link only (a file imports the changed file). Every target
  carries its `reason`, its distance and the `via` chain from the change.
- **Changes are attributed to units, not modules.** A one-line edit to a private constant reaches
  the declarations that use it, not every importer of its module. Comment and formatting edits are
  inert; an edit that runs code on load, reorders imports or changes a directive is not. Nor is
  added code that rebinds a name existing code reads as a global, or that exports a value from a
  module another one reads whole (`import * as`, `export *`, `import()`, `require()`).
- **Absence is never evidence.** `explicitlyUnaffected` is always empty. A surface is `not_reached`
  only on a complete, untruncated reach; every place the modeled reach stops (depth or target
  bounds, unscanned or non-literal module links, languages without call edges) is named in
  `unresolved`.
- **The report is bound to the index it read.** `analysis.binding` is `bound` or `broken` with
  named breaks (another commit, an index that missed or read other content, a change during the
  analysis). A broken binding nulls every index-derived field and has confidence `none`.
- **Confidence is a projection, not a probability:** `moderate` is the ceiling for static reach,
  `low` when a gap stops the reach, `none` when the binding is broken.
- An optional surface map (`--surfaces`) names parts of the repository; surfaces are never
  inferred. Authored invariants and markers reached by the change are listed as exposed claims
  with their tier.

The report contains no proof verdict, proof level, test obligation, proof count or allow/block
decision. Which proof a change needs, which tests must run and whether it may proceed remain the
consumer's policy. The [reference](../reference/change-impact.md) gives the consumer reading rules,
every code, and a worked example on `examples/change-impact-replay`.

`verify` is unchanged: its computation now shares the diff and binding code with `impact diff`
(source resolution and index-binding observation) behind characterization pins recorded at
`v0.3.1`, including the working-diff seal, and its strict diff parser keeps its input contract.

## Compatibility and limits

The CLI, MCP package and both supported plugins advance together to 0.3.3; the generated plugin
runtimes embed the CLI and gain `impact diff`. The change is additive: no existing command, output
or configuration changes. Within `schemaVersion: 1`, later additions are optional fields and new
codes in the open code sets; consumers must treat an unknown code as opaque and bounding, never as
absence. There is no MCP tool and no `--from-file` input in this release.

Reach is static: dynamic dispatch, reflection, function values, configuration, data and runtime
state are not modeled; cross-file reads of constants and types are visible only as file imports;
Python has no call reach (`language_has_no_call_edges`). These limits are carried in every report
under `analysis.limits`.

The evidence position of v0.3.1 is unchanged. Mac/lobby performance, incremental indexing, full
resource budgets and human outcomes (adoption, retention, comprehension and contribution time)
remain **NOT_MEASURED**. No measurement of how often `ChangeImpact` narrows a planner's proof
effort in practice is claimed. Oh My Pi support remains **experimental** and outside the
Codex/Claude stable-delivery attestation.

## Publication evidence and rollback

The [tag-driven release workflow](https://github.com/hoklims/semctx/actions/workflows/release.yml)
verifies the annotated tag, publishes the exact npm tarball, checks its `gitHead`, advances `stable`
without force, creates the GitHub Release and then verifies installation through Codex and Claude
in isolated homes. The workflow result is the authority for publication and host delivery; source
code and local verification alone establish neither.

For a runtime rollback, pin the preceding release with `bun add --global semctx@0.3.1` and replace
only the Semctx marketplace in the relevant host profile with the immutable `v0.3.1` tag, as
described in the [v0.3.1 brief](v0.3.1.md). A rolled-back CLI no longer has `impact diff`. Do not
force `stable` or rewrite a published tag.
