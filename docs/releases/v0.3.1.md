# v0.3.1: guarded content proof inside project-managed hook chains

Semctx 0.3.1 lets guarded mode coexist with a project's own Git hook manager (Lefthook, husky) by
carrying the content proof into the hook chain itself, and it closes the hook-bypass gap on both
guarded verbs. It changes no index format, verification-state format, MCP tool or JSON contract.

## Install or upgrade

Semctx 0.3.1 requires Bun >=1.4.0. Pin the release when reproducibility matters:

```bash
bunx semctx@0.3.1 install
```

Plugin installation does not reload an active agent session. Open a new Codex task, or run
`/reload-plugins` in Claude Code and restart if reload fails. The guard changes below apply to
sessions started after the plugin is reinstalled.

## What changed

Guarded mode (ADR 0007) refused to authorize `git commit` or `git push` while the repository's hooks
directory held anything but Git's `*.sample` files, which made it unusable next to any real
Lefthook or husky install. A repository can now declare `{ "enabled": true, "hooks":
"project-managed" }` in `.semctx/guard.json`. Under that declaration the sample-only rule no longer
applies; without it, nothing changes. Any other `hooks` value keeps enforcement on with the default
rule (ADR 0029, GitHub issue #169).

`semctx verify hook pre-commit`, run as the last job of the project's pre-commit chain, observes the
index after the last writer, which is the tree Git is about to record. It refuses a partial index
before any analysis, returns without analysis when a non-`BLOCK` record already covers that exact
tree, and otherwise records a new working-tree verification under the same rules as
`verify diff --record`. Exit `0` when covered or recorded non-`BLOCK`, `3` on `BLOCK`, `1` when the
hook cannot vouch for the commit.

`semctx verify hook pre-push` never records. It reads the ref lines Git pipes into the hook and
requires the tree of every pushed commit to equal the recorded verified state; deletions, unproven
commits, non-commit objects and an unreadable stdin are refused. The plugin's pre-tool guard keeps
both of its tree checks: the commit-time check forces a fresh proof, and the push-time check is what
catches a writer that ran after the semctx job (`HEAD` no longer materializes the recorded state).
The remedy is the hook order, never a post-commit record, which would only re-stamp the tree.

Hook bypass is non-authorizing in every guarded profile: `git commit --no-verify` / `-n`
(including short clusters carrying `n`) and `git push --no-verify`. Push previously listed
`--no-verify` as a safe option; commit did not inspect it. `git push -n` stays `--dry-run`.

Taking the proof into the hook chain also gates a human `git commit` / `git push` in that
repository; that is the declared integration, chosen by the project. `post-commit` and
`post-rewrite` hooks can still publish an unverified tree from inside the chain, and a human
`--no-verify` bypasses the chain outside the plugin. These residues are named in ADR 0029.

## Compatibility and limits

The CLI, MCP package and both supported plugins advance together to 0.3.1. `guard.json` gains one
optional key; existing files behave identically. `verify hook` adds text output and exit codes only;
`verify diff` and every versioned JSON contract are unchanged. In guarded mode the bypass change is a
tightening: a `--no-verify` commit or push that the guard would previously have authorized is now
refused.

The evidence position of v0.3.0 is unchanged. Mac/lobby performance, incremental indexing, full
resource budgets and human outcomes (adoption, retention, comprehension and contribution time)
remain **NOT_MEASURED**. The earlier thirty-change pilot keeps its **UNKNOWN** labels and
establishes neither accuracy nor benefit. Oh My Pi support remains **experimental** and outside the
Codex/Claude stable-delivery attestation.

## Publication evidence and rollback

The [tag-driven release workflow](https://github.com/hoklims/semctx/actions/workflows/release.yml)
verifies the annotated tag, publishes the exact npm tarball, checks its `gitHead`, advances `stable`
without force, creates the GitHub Release and then verifies installation through Codex and Claude
in isolated homes. The workflow result is the authority for publication and host delivery; source
code and local verification alone establish neither.

For a runtime rollback, pin the preceding release with `bun add --global semctx@0.3.0` and replace
only the Semctx marketplace in the relevant host profile with the immutable `v0.3.0` tag, as
described in the [v0.3.0 brief](v0.3.0.md). A rolled-back guard restores the sample-only hooks rule,
so a repository that declared `hooks: "project-managed"` is refused again by the older plugin until
the hook manager is removed or the plugin is upgraded. Do not force `stable` or rewrite a published
tag.
