Act one · the change

Two characters. Every caller that handled the empty case is now wrong, and the type checker will not tell you which ones mattered.

Constraints you write. Enforcement you don't.

semctx never guesses what matters in your codebase. You say it, in one line of English, and it becomes a machine-checkable rule for everyone who touches that code afterwards.

A sentence in a comment is the entire configuration. No schema. No dashboard. Nothing inferred by a model.

Contracts, invariants and capabilities come from explicit, machine-readable markers — never LLM inference. That is what makes the verdict deterministic and traceable: the same repository state produces the same answer, byte for byte, on any machine.

Markers are optional. Without them semctx still reports impacted symbols, exported contracts and statically linked tests. What a marker buys you is the right to stop a commit — and it is deliberately you who grants it, symbol by symbol.

That asymmetry is the design: an analyzer that cannot invent importance, and an author who can declare it in seconds.

Strict → BLOCK invariant_touched_without_test

Invariant-constrained code changed with no eligible statically linked test.

armed by @invariant
Strict → BLOCK critical_contract_changed_without_test

A critical exported contract changed with no eligible statically linked test.

armed by @tag critical
Strict → BLOCK security_surface_without_verification

A security surface changed without an explicit verification.

armed by @tag security
Advisory → WARN contract_changed_without_test

Any exported interface or type changed with no linked test. This one needs no marker at all.

on by default
Advisory → WARN contradiction_unresolved

The change leans on a source that a later decision contradicts.

on by default
That is the whole set five rules · two tiers

There is no score, no threshold, no confidence percentage. A verdict is the union of rules that fired, and each one names itself.

PASS → 0   WARN → 0   BLOCK → 3

Three places, one engine.

The CLI and the agent tools are thin transports over the same analysis. Same rules, same reason codes, same verdict.

In your terminal

Working tree, staged commit, or a range against a real merge-base. Text, JSON or GitHub output. An optional pre-commit hook stops the commit only on BLOCK.

semctx verify diff --base origin/main

Inside your agent

Plugins for Claude Code and Codex expose the same tools over MCP, so the agent verifies its own diff. Guarded mode holds git commit until the change is verified.

A cooperative soft gate — not a sandbox, not a boundary against a hostile agent. The repo says so first.

On every pull request

A composite Action posts annotations and a job summary. WARN never fails the check; BLOCK does. No PR comments, no secrets, contents: read only.

Planning and reconciliation tools report executionAuthority: "none". semctx never edits, commits, deletes or deploys anything. A verdict is a verdict, never a permission.

We ship the list of things it cannot do.

What it does
  • Maps a diff to the symbols, contracts, invariants and tests it touches.
  • Gives a PASS / WARN / BLOCK verdict you can read the reasoning of.
  • Runs locally, from coding agents, and in CI.
  • States what it cannot prove, as Unknowns, instead of staying quiet.
What it does not
  • Replace search engines or semantic retrieval. Use grep or embeddings for that.
  • Claim full repository understanding.
  • Require an LLM.
  • Upload your code, comment on PRs, or need a secret by default.
We published a benchmark we lost

semctx used to also answer "which files matter for this task?". We tested it on 16 real commits against a plain text search. It lost on every measure.

The reason was structural: it read names, never file contents. So we removed the feature instead of tuning it, and left the losing numbers in the repository. That is the standard the rest of this page is written to.

Static, not dynamic

It reasons about the diff without building or running the code. It selects what to re-test; it does not tell you the code still works.

Selection, not coverage

Recommended tests come from imports inside test files. They are candidates — never executed, never measured coverage.

TypeScript first

TypeScript gets full semantic analysis. Python is an opt-in syntax vertical through 3.12 — it does not infer calls or coverage.
